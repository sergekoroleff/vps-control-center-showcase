# VCC 6.1 — Automatic VPN Provisioning: engineering status

**Status as of 21 November 2026:** **In development — NOT released.**  
**Focus:** repeatable, secure AmneziaWG 3.1 peer provisioning and automatic Telegram `.conf` + QR delivery.

## What is already demonstrated

- VCC's owner-only Telegram VPN Wizard has delivered a **real configuration file and a branded QR code**; its owner later confirmed that the earlier client works.
- Backend components for signed requests, encrypted result storage, delivery relay and Telegram document/photo sending are operational in the earlier controlled workflow.
- The existing private VPN clients have been preserved while developing the follow-up automatic workflow.

These are real capabilities, but they **do not establish** that creating every subsequent VPN client is now fully automatic.

## What remains incomplete

- A later VPN peer was successfully created, but its encrypted result was **not confirmed as delivered** to the Telegram owner.
- The new background task consumer currently has an unresolved recovery-first state-machine gap, and unattended periodic processing has not been accepted.
- The Telegram Wizard still requires an additional user action to send available attachments; durable automatic push has not yet been released.
- The earlier ambiguous delivery failure is not yet traced to a conclusive stage.

## Engineering milestones recorded on 21 November

1. Confirmed the existing HTTPS delivery path reaches the intended receiving service.
2. Introduced restricted diagnostic classifications for transport and receiving-service errors, with no credential or profile content in logs.
3. Corrected a documented mismatch in the accepted signed-acknowledgement response field in the deployed US consumer. This patch has **not yet passed a successful live delivery acceptance**.
4. Designed a recovery-first approach that recognizes a previously committed VPN peer and resumes **delivery**, rather than generating duplicate keys and creating another peer.
5. Established explicit acceptance criteria for automated private Telegram `.conf`/QR push, crash-safe delivery tracking and true device connectivity.

## Release acceptance checklist

- [ ] Existing committed client's encrypted profile is recovered and delivered **without creating a duplicate VPN peer**.
- [ ] Signed acknowledgement and durable records agree on the outcome.
- [ ] The bot **automatically** sends both a valid configuration document and a QR code to the authenticated owner.
- [ ] The VPN profile connects on a real device, a real website loads through the tunnel, and previous clients remain functional.
- [ ] One new owner-approved client is provisioned end-to-end from the Telegram wizard with **no terminal commands per request**.
- [ ] A restart, repeated click or transport ambiguity does not duplicate clients.
- [ ] The production worker and monitoring are enabled only after controlled acceptance.

## Privacy and scope

This public progress report intentionally excludes real server endpoints, private client names/IDs, complete command hashes, keys, configurations, ciphertexts, token values, full QR images and unreleased private code.

**Next roadmap after this P0:** owner-only access revocation in the bot, followed by a read-only VPN client overview in the Mini App. Neither is represented as shipped.
